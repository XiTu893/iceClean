# IceClean 面板功能与交互全面提升方案

> 版本：v1.0（待确认）
> 目标：全面对标业界系统（360 安全卫士 / CCleaner / Wise Care 365 / Dism++），做到**功能强大、交互简单友好**。
> 核心原则：**任何耗时操作都必须有"过程实况"反馈**——用户应始终知道程序正在处理哪个文件/路径、进行到哪一步、还要多久，杜绝"点了按钮就没反应"的黑盒体验。

## 三、统一基础设施建设（P0，所有面板受益）

### 3.1 ActivityTicker —— 全局扫描实况控件

将现有 `ScanInfoPanel` 泛化为通用实况组件 `src/gui/controls/ActivityTicker.{h,cpp}`：

```
┌──────────────────────────────────────────────────────────┐
│ ⟳ 正在扫描软件缓存 · 已发现 1,284 项 · 35.6 MB    [⏸][✖] │  ← 状态行(主色)
│    C:\Users\x\AppData\Local\npm-cache\cacache\index-v5…  │  ← 实况行(灰色，中部省略)
│ ━━━━━━━━━━━━━━━━━━━━╸────────────── 62% · 约12秒          │  ← 进度行(可选)
└──────────────────────────────────────────────────────────┘
```

API：
```cpp
void StartPhase(const wxString& phaseName, int estimatedUnits = 0); // 进入阶段
void Tick(const wxString& currentItem, uint64_t bytesSoFar = 0);    // 实况节拍（内部节流~120ms）
void SetPhasePercent(double pct);                                   // 阶段百分比
void Pause(); void Resume(); void Finish(const wxString& summary);
```

约束：
- 内部节流，工作线程随便调 `Tick()`，绝不刷爆事件队列（复用 DeepClean 已验证的 CallAfter+steady_clock 节流模式）
- 所有扫描类面板**只准用这一种**实况展示，禁止再造轮子

### 3.2 ProgressBus —— 统一进度事件模型

扩展现有 `wxEVT_SCAN_PROGRESS_UPDATE` 为通用负载：

```cpp
struct OpProgress {
    wxString opId;          // 操作实例 id（区分多面板并发）
    wxString phase;         // 阶段名："检测C盘大文件夹"
    int phaseIndex, phaseCount;
    long long unitsDone, unitsTotal;   // 文件数/字节数
    wxString currentItem;   // ★ 当前正在处理的路径——"FTP下载式"反馈的核心字段
    uint64_t bytesProcessed;
};
```

- core 层新增约定：**所有 Detect()/Scan()/Clean() 重载增加 `OpProgressSink` 参数**（std::function，线程安全、自带节流由 Ticker 侧负责）
- 迁移器、重复文件、卸载残留等全部改造为可上报 `currentItem`

### 3.3 取消/暂停令牌统一

现有两套机制（aggregator stopFlag、DeepClean atomic pause）合并为：

```cpp
class OpToken {  // 传引用进 core
    std::atomic<bool> cancelRequested, pauseRequested;
    void WaitIfPaused();  // 复用 DeepCleanPanel::WaitIfPaused 逻辑上移到 utils
};
```

- **修复智能迁移停止无效 bug**：MainWindow 的迁移扫描分支从未调用 `LargeFolderDetector::Cancel()`，停止按钮只对类型0扫描生效（MainWindow.cpp:574-602 分支缺失）

### 4.4 启动加速 StartupPanel（P1）

#### 4.4.0 已确诊缺陷与修复记录（本节为实测分析结论）

**用户报告**：禁用「electron.app.LM Studio」等启动项后点优化，刷新列表仍显示未优化状态。

**根因链（三项叠加）**

| # | 根因 | 机理 |
|---|---|---|
| 1 | **破坏式禁用 vs 应用自愈** | 旧实现把 HKCU Run 值删除移入 `IceClean\DisabledStartup` 备份。Electron 应用（LM Studio 实测 Run 值名即 `electron.app.LM Studio`）的自启由自身设置驱动，下次启动应用会把 Run 值重写回来 → 刷新后"复活"，看起来从未生效 |
| 2 | **读侧无视权威状态** | `GetStartupItems` 硬编码 `isEnabled=true`，从不读 Explorer 的 `StartupApproved` 标志；任务管理器里已禁用的项在本应用中恒显示启用，自家禁用后条目又整体消失而非显示"已禁用" |
| 3 | **失败静默** | `DisableItem` 多路径返回 false（值读取为空/文件占用），完成提示只报成功数，失败项零痕迹 |

**修复方案（已实施）**

1. **禁用语义切换为任务管理器同款机制**：向 `HKCU\...\Explorer\StartupApproved\Run` 写入 12 字节标志（首字节 0x03 + FILETIME）。Run 值原样保留 → 应用重写无效，Explorer 登录时依据标志跳过。恢复=删除标志。启动文件夹项对应 `StartupApproved\StartupFolder`
2. **读侧以标志为准**：列表状态反映真实启用态；旧版备份键中的条目兼容识别
3. **失败可见化**：MainWindow 收集逐项失败清单，完成对话框列出（含原因提示）；操作日志追加失败计数；同时移除了禁用时顺手杀进程的越权副作用
4. （前置修复回顾）服务禁用曾传显示名给 OpenServiceW，已改传服务键名并增加回读验证

**验证手段（不依赖 gtest 的命令行工具）**

- 新增 `tools/startup_optimizer_cli.cpp` + 根目录 `run_startup_checks.bat`：
  - `run_startup_checks.bat` → 沙箱自检 9 项（非破坏性、幂等、往返恢复、未知项诚实失败、旧机制兼容…），当前 **9 passed / 0 failed**
  - `run_startup_checks.bat --list` → 真机只读诊断。实测输出确认：`electron.app.LM Studio` 存在且为 ON；系统中 3 个已被标志禁用项正确显示 OFF，证明读侧集成正确
- gtest 用例同步保留于 `tests/optimizer/test_startup_optimizer.cpp`（BUILD_TESTS 开关默认关）

## 八、M1 落地记录与 CLI 验证结论（新增）

### 8.1 已实施项
1. **迁移扫描全程实况**：`LargeFolderDetector` 回调升级为 `(path, foundCount, foundBytes)` 并支持 `DetectAt(根目录)`；MainWindow 迁移扫描分支按阶段（大文件夹→微信→QQ→Steam→用户文件夹）经 `wxEVT_SCAN_PROGRESS_UPDATE` 节流上报，MigrationPanel 新增 ScanInfoPanel 实况条实时显示"当前阶段 · 已发现 N 项 + 正在遍历路径"
2. **迁移扫描停止修复**：MainWindow 注册活动 detector 指针，OnScanStop 同步调用 `Cancel()`——此前迁移页停止按钮完全无效
3. **深度清理一键扫描「停止」**：新增 m_scanCancelled 原子标志与「停止」按钮；软件缓存扫描传入 stopFlag 按文件粒度中止；WaitIfPaused 响应取消；完成态区分"已停止/扫描完成"
4. **仪表盘/聚合器链路复用**：既有进度广播同时驱动迁移面板

### 8.1.1 二次修正：流式测量（用户实测反馈"扫描无细节进展"后补）
初版回调挂在一次性 `GetFolderSize` 之后——统计 C:\Users 这类大目录本身耗时数十秒且期间零回调。已改为 `MeasureDirectory` 流式测量：递归统计大小的同时**每进入一个子目录即上报当前路径**（跳过 reparse 防重复计数），UI 侧 120ms 节流消费。CLI 新增断言 `streaming ticks reach nested subdirectories` 验证深层 tick。

### 8.1.2 与原方案的偏差说明（诚实记录）
- **ActivityTicker 独立控件未抽取**：直接复用了 ScanInfoPanel（能力等价），避免重复控件；M2 若第三处需要再泛化
- **OpToken/ProgressBus 统一抽象未落地为独立类**：各处使用作用域内 atomic 标志 + 既有事件通道达成同等语义；待 M2 多面板接入出现真实重复时再提炼

### 8.2 CLI 验证发现并修复的生产级缺陷
| 缺陷 | 后果 | 修复 |
|---|---|---|
| `JunctionPoint::Create` 重解析缓冲区布局不合规（FSCTL 返回 4392 ERROR_IO_REPARSE_DATA_INVALID） | **历史上所有 junction 迁移实际从未成功**（建链失败回滚） | 按规范平铺布局重写：SubOff=0/SubLen 不含null/PrnOff=subLen+2/DataLength=names+12/null 终止符齐全；Remove 同步修正头部大小误用 GUID 常量问题 |
| `LargeFolderDetector` 进度回调在入列前触发 | UI 计数恒为 0 | 回调移至入列后 |

### 8.3 验证工具与结果
- `run_core_checks.bat`：默认沙箱模式（写入仅限 `HKCU\Software\IceClean\CliTests` 与 `%TEMP%\IceCleanCli*`），覆盖注册表工具 / StartupApproved / 大文件夹检测（父子去重）/ Junction 原语 / 服务枚举(只读) / 启动项读取(只读)
- `run_core_checks.bat --with-migration`：追加跨盘迁移端到端（复制→删源→建链→双向可读→清理）
- 当前结果：**28 passed / 0 failed**；`run_startup_checks.bat`（StartupApproved 机制回归）9 passed / 0 failed
- 安全设计遵循用户要求：默认模式零系统风险，E2E 显式启用且仅操作自建目录

## 六、风险与兼容

1. **core 层接口变更**（Detect/Scan 加 sink 参数）：全部带默认值 nullptr，旧调用零破坏
2. **线程纪律不变**：Ticker 内部 CallAfter，core 严禁直接碰 UI（沿用现有红线）
3. **性能**：Tick 节流 120ms + 每 N 条回调（沿袭 ScannerBase 每10文件一次），实测开销 <1%
4. **junction 撤销**属危险操作，默认仅生成记录不开放一键撤销入口，M2 评审后再定

## 七、总验收清单

- [ ] 应用内**不存在任何超过 2 秒且无过程反馈的操作**
- [ ] 所有扫描均可停止；长扫描（>30s 预估）均可暂停
- [ ] 每个完成动作有量化报告（数量/字节/耗时）
- [ ] 危险操作 100% 走 ConfirmDialog + 还原点 + OperationLogger（既有红线保持）
